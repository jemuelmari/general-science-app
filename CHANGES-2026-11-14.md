## How to deploy (do these in order)

1. **Website (GitHub) first** — upload / push every file in `changed-files-part2.txt` (or the whole folder).
   Remove these files from the repo if they are still there:
   `fix-competencies.js`, `fix-all-competencies.js` (old scripts that rewrote the question banks with a 30:70 ratio),
   `ssets/` (typo folder), `assets/js/item-analysis-engine.js`, `assets/css/item-analysis-engine.js`,
   `.github/workflows/revert-exams.yml`.
   Wait until GitHub Pages shows the new version (open any quiz page — it should show `v1.2.0`).
2. **Backend (Google Apps Script)**
   1. Replace all of `Code.gs` with `backend/google-apps-script/Code.gs` (v1.12.1).
   2. In `CONFIG`, set `VERIFY_SINCE` to the date and time the new site went live in step 1,
      e.g. `'2026-11-15T18:00:00+08:00'`. Attempts before that time are never key-checked.
   3. *(Only if Term 1 PT1 was already submitted by students)* set `PT1_FIX_CUTOFF` in **both**
      `Code.gs` (CONFIG) and `config.js` to the date/time when **Term 2 PT1** was really opened.
   4. In the editor choose `testAnswerKey` → **Run** once → allow the permission
      ("connect to an external service"). The log should say `OK — 20 answers read…`.
   5. **Deploy → Manage deployments → ✏️ Edit → Version: New version → Deploy** (same URL).
   6. If you set `PT1_FIX_CUTOFF`: choose `fixTerm1PT1` → **Run** once.
3. **Teachers:** log out and log in again once.
4. **Students:** nothing to do. Pages are network-first; old cached lessons and tests refresh automatically.

## What changed in part 2 (content revision)

### Lessons — all 30 weeks (Terms 1–3)
- Every day now has its **own discussion** (Day 1 introduces, Days 2–4 each teach a new part), followed by the activity.
  Discussions are about 150–200 words of text plus tables; with the explanations after each answer, students read roughly 250–350 words per day.
- Every activity item has an **explanation**, every match pair has a **reason**. Choices are shuffled per attempt; no letter prefixes in the data.
- Choice lengths are balanced: the correct answer is the single longest choice in **23 of 420** multiple-choice activity items (5%).
- Filipino contexts throughout (jeepney, sari-sari store, barangay, PAGASA/PHIVOLCS, local places and species).
- Fixed facts while revising: rolling = translational **and** rotational (Term 1 Week 2); Term 3 Week 9 now uses PAGASA's real
  **iHeatMap (Interactive Heat Index Mapping and Prediction)**, launched April 2025 — the old page called it a "Heat Index and Hazard Assessment Tool".

### Quizzes, STs, Term Exams — all 18 banks (same file names, same item IDs)
- Exactly **70% LOTS : 30% HOTS** in every quiz (14/6), ST (21/9) and TE (42/18). HOTS items are real scenarios: calculations, cause-and-effect, judging claims, choosing the best plan.
- Only in-scope competencies. Each competency only uses Bloom levels allowed for it in `data/competencies.json`.
- STs follow the TOS order exactly (8-8-7-7 items per competency); the TOS answer key now has **0 mismatches** for every ST.
- Correct answer is the strictly longest choice in **0–10%** of items (it was **62%** of the 540 old items). No duplicate items (Term 3 TE q26/q37 duplicate gone).
- Term 3: ST2 now covers Weeks 5–8 (Week 9 is a TE competency), Quiz 2 covers Week 4, and the W1/W3/W4 competency statements match the weekly lessons.

### Engine / analysis
- **TOS**: equal-hour ties keep the 8-8-7-7 order; when the published bank fits the TOS row, the Bloom counts shown come from the actual questions (tagged "from question bank"). `weeks` in `competencies.json` no longer overlap, so Term 1 Week 4 no longer appears in ST2.
- **Item Analysis**: answers given on an older version of a revised test are left out of the item table (they would point at the new question) and the page says how many; they still count in competency MPS and Most/Least Learned.
- **Grade integrity (backend v1.12.1)**: every attempt carries a short fingerprint of the answer key it was taken with. The server checks answers against the published key only when the fingerprint matches, so an honest attempt is never marked wrong because of a revision or the 6-hour key cache.

## What changed in part 1

### Grading
- Transmutation: raw 70 → 75 … raw 100 → 100 (linear), below 70 = raw + 5. The old table gave raw 77–80 a *lower* grade than raw 76.
- Passing raw score is **70%** everywhere (`CONFIG.PASSING_PERCENT`): quiz/ST/TE lock, activities, evidence.
- One grade formula (`Transmutation.computeTermGrade`) and one data source (`TeacherCloud`) for Class Record, Grading Sheet, Reports, Assessment Tracker and Intervention. PT grades now appear in all of them.
- **Score Entry (new page `teacher/score-entry.html`)**: type paper-and-pen scores (quiz, ST, TE, PT). They are marked **P / PAPER**, replace the online score (may be lower) and can be removed. Paste-many-scores supported.
- Print Exam: new **Answer sheet** (bubble sheet) — alone, with the test, or with test + key.
- Sync Center "Apply" / "Import" now save to the cloud gradebook (before: only the teacher's browser).

### Analysis
- **Item Analysis** rewritten: quizzes included, section/set filters, difficulty (p), discrimination (D, upper/lower 27%), distractor counts, retain/revise/reject, per-competency MPS with code + full statement, CSV.
- **Most & Least Learned** (TOS Generator and Class Record) are competency-based from ST1 + ST2, top 5 / top 5 with code + statement. Items are matched by question ID (the old code used the shuffled position → wrong competency).
- **TOS**: 70 % LOTS : 30 % HOTS, balanced so the whole test hits the ratio exactly. Every competency now allows Remembering/Understanding (`data/competencies.json` v1.1.0).

### Assessments (student side)
- Term Exam could be re-taken after passing (score was stored as `te.te`) — fixed.
- Time-up no longer locks a *passing* attempt as "tab-switch / Tampered"; it locks only below 70%.
- Reloading the page no longer restarts the timer or the tab-switch count; answers are resumed. Timer follows the real clock.
- If `randomize.js` cannot load, the test does not start (no more random order that differs from the printed Set A/B).
- **Term 1 PT1 saved as Term 2** — fixed (+ optional migration above).
- Exam Evidence now finds Term Exam records.

### Lessons
- Day 2–4 now carry their own discussion (sample: Term 1 Week 1). Activities: choices shuffled each attempt, no more "A. A)", and **an explanation after every answer**; match pairs show their reason.

### Security & reliability
- Teacher-only backend actions require the teacher token (term access, PT grades, locks, attempts, PT files, overrides…).
- Student names are cleaned on the server and HTML-escaped on every teacher page (a crafted name could steal the teacher password).
- A student device can no longer rename an existing student or change section; Normalize Names (teacher) still can.
- Expired approved retake codes no longer block a new request.
- Row-deleting backend actions run under the script lock.
- Offline queue no longer loses an attempt submitted during a sync; failing items retry every 10 min.
- Service worker installs again and is network-first (students get updated questions/lessons); manifest icons fixed; broken teacher redirects fixed; workflows have write permission; cache-bust runs for any JS/CSS change.

## Remaining limitations
- **Old attempts vs new questions.** Students who already took a Term 1/Term 2 quiz, ST or TE keep their scores. Their item data refers to the old questions, so Item Analysis for those tests starts fresh with new attempts.
- **Printed tests already given** used the old questions. Reprint from Print Exam for any test you still have to give.
- **Term Exam vs TOS.** The TE bank is fixed (6 items per competency, all 10 competencies). The TOS for the TE is built from the top 5 least-learned + Weeks 9–10, so its rows will not match the fixed bank. A future "build TE from TOS" option would pick items per competency.
- **Grades are still scored on the student's device.** The server recomputes the score and checks answers against the published key, so editing the score or the "expected" answers no longer works. But the answer keys are public JSON, so a student who reads them can still answer everything right; a signing key (HMAC) cannot fix that because anything in a static page is readable. Only server-side scoring with hidden keys would close it — a bigger redesign (it would also end offline test-taking).
